# 自定义块与包重建设计

> 状态：**共识冻结，等待按本文重构**。本文是 Custom Block 数据、编辑、解析、渲染、预览以及资源环境的唯一设计依据。本文确认的是目标协议，不代表当前代码已经符合。与本文冲突的旧文档按第 14 节删除，不保留兼容概念。

## 1. 核心定义

必须区分两个概念：

- **自定义块结构（Custom Block structure）**：存储在 `.ocblock` 中的可复用实现定义，由 `scheme` 和 `root` 组成。
- **自定义块（Custom Block）**：和 text、image、container 等基础 Block 身份相同的正式 Block。它拥有 `id`、`type`、结构文件引用、该结构的 `scheme` 所定义的字段，以及用户为它创建的附加字段。

Custom Block 不是等待在 parser 前被替换掉的引用 wrapper，也不是预先展开的 native subtree。它必须作为正式成员进入 Stored Block、Binding、RenderReady 和 renderer 协议，并拥有 `CustomBlockRenderer`。

包是另一个概念：

- `.ocblock` 定义一个 Custom Block 的字段协议和内部结构，不包含资源字节、发布者、版本或接口哈希。
- `.ocpack` 是一个资源环境的运输边界，可以包含字体、图标、图片、Custom Block 和直接子包依赖。
- 两者不能互相代替，也不共享生命周期。

## 2. Custom Block 的存储身份

文档中的 Custom Block 与普通 Block 一样是稀疏、可直接 JSON 读写的 record：

```ts
type CustomBlock = CardBlockBase & {
  type: 'custom-block'
  customBlockKey: CustomBlockKey
  additionalFieldDefinition?: AdditionalFieldDefinitionMap
  // 当前 `.ocblock.scheme` 定义的字段值和其他实际字段直接位于 record 顶层
}
```

约束如下：

- `customBlockKey` 的地位等同于 Image Block 的 `image`：它是这个 Block 的普通结构引用字段，可以选择和更换。
- `scheme` 定义的字段直接存储在 Custom Block 顶层，不放进 `values`、`properties`、`parameters` 或 override 容器。
- 蓝图中的字段值仍存储在 Block record；实例覆盖仍由文档上层的 `instance.data[blockId]` 保存。Custom Block renderer 不知道蓝图和实例。
- `additionalFieldDefinition` 与其他 Block 的附加字段机制完全相同。它不是 `.ocblock.scheme`，也不能替代 `.ocblock.scheme`。
- 存储层不按当前 `scheme` 删除、补齐、归一化或迁移字段。更换结构文件后，旧字段仍可留在 record 中。

## 3. `.ocblock` 唯一结构

`.ocblock` 是纯 JSON。顶层至少包含结构身份、`scheme` 和 `root`：

```ts
type CustomBlockDefinition = {
  type: 'opencard-custom-block'
  key: string
  structureName: string
  scheme: Readonly<Record<string, CustomBlockFieldDefinition>>
  root: CardBlock
  declaredResourceDependencies?: readonly string[]
}
```

推荐实例：

```json
{
  "type": "opencard-custom-block",
  "key": "notice-card",
  "structureName": "Notice Card",
  "scheme": {
    "title": {
      "fieldType": "string",
      "categoryId": "content",
      "multiline": false
    },
    "accent": {
      "fieldType": "color",
      "categoryId": "surface"
    },
    "width": {
      "fieldType": "string",
      "categoryId": "size",
      "autocomplete": ["auto", "100%", "240px"]
    }
  },
  "root": {
    "id": "root",
    "type": "simple-container",
    "title": "Notice",
    "accent": "#2f6fed",
    "width": "240px",
    "background": "{{self:accent}}",
    "children": [
      {
        "id": "title",
        "type": "text-block",
        "content": "{{parent:title}}"
      }
    ]
  },
  "declaredResourceDependencies": []
}
```

这里的 `scheme` 承担基础 Block 内置 scheme 的同等职责：说明 Custom Block 可以持有哪些正式字段、字段类型以及 PropertyEditor 需要的编辑约束。区别仅是基础 Block scheme 编译在软件中，而 Custom Block scheme 在打开结构文件时即时取得。

### 3.1 资源所有权与引用

```text
项目/
└── .opencard/
    ├── fonts/fonts.json
    ├── icons/icons.json
    ├── blocks/
    │   ├── blocks.json
    │   └── notice-card.ocblock
    └── packages/
        └── theme-pack/
            ├── .opencard/manifest.json
            ├── .opencard/blocks/blocks.json
            ├── .opencard/blocks/notice-card.ocblock
            └── assets/
```

- `blocks.json` 只登记当前环境拥有的结构；包内结构不能复制进宿主 `blocks/` 冒充本地所有权。
- 包内结构只读；“复制为本地块”是改变所有权的显式操作。
- `customBlockKey` 必须经过共享 Custom Block key parser/resolver，业务代码不得手写 `split`、`startsWith` 或 fallback 查找。
- 当前环境的结构使用 `block:key`；直接子包结构使用 `packageKey@block:key`。裸 key、`package/block`、旧 `source` 和 `interfaceHash` 都不是合法身份。
- 同一引用原则适用于 asset、font、icon 和 block；resolver 同时返回资源与其定义环境。
- 包 manifest 记录包身份、公开资源索引、直接子包依赖和内容哈希；卡牌引用不锁定包版本，升级以同 key 环境的原子替换为单位。

## 4. `scheme` 字段协议

### 4.1 与内置 scheme 对齐

`.ocblock.scheme` 应复用软件内置 Block scheme 的字段定义形状和解释器，包括适用的：

- `fieldType`
- `categoryId`
- `isHidden`、`isReadonly`、`required`、`resettable`、`deletable`
- string 的 `minLength`、`maxLength`、`options`、`autocomplete`、`multiline`、`richText`
- filePath 的长度和文件过滤约束
- number 的 `min`、`max`、`step`
- 其他已注册 fieldType 的对应编辑约束
- 必要时的 `bindingScopes`

但 `.ocblock.scheme` 不保存：

- `defaultValue`：Custom Block 字段没有第二份 scheme 默认值；未覆盖时保留 `.ocblock.root` 的实际值。
- `acceptsBinding`：Binding 能力由统一字段类型和结构策略决定，不能在 `.ocblock` 中维护第二套开关。
- Vue 组件、编辑器实例、command、预览状态或资源对象。

`fieldType` 必须存在，因为它同时服务字段编辑、Binding 值类型校验以及 Custom Block 自身的 RenderReady 解析。

### 4.2 `scheme`、附加字段和 Other

PropertyEditor 的字段归类顺序固定为：

1. Custom Block 自身的结构字段，如 `id`、`type`、`customBlockKey`。
2. 当前 `.ocblock.scheme` 中声明的正式字段。
3. 当前 Block 的 `additionalFieldDefinition` 中声明的附加字段。
4. record 中仍存在但前三者均无法解释的字段，归入 **Other** 分类。

因此更换 `customBlockKey` 后无需迁移：

- 新 scheme 中存在的字段立即按新定义编辑。
- 新 scheme 不再认识、同时也没有附加字段定义的旧字段进入 Other。
- 存在附加字段定义的字段仍按附加字段编辑。
- scheme 声明了但 root 没有同名顶层字段时，字段仍是 Custom Block 的合法字段；渲染时因没有覆盖目标而直接忽略，不制造虚假 root 字段。

Other 分类需要补齐所有支持语言的 i18n，但分类缺失不改变上述数据语义。

### 4.3 root 和后代字段

- `scheme` 只定义 Custom Block 载体可持有的字段，不是对整棵 root subtree 的深度字段清单。
- renderer 的直接字段覆盖只检查 `root` 的顶层字段。
- root 后代 Block 的全部字段和 `additionalFieldDefinition` 都是 `.ocblock` 内部实现，不能自动暴露为 Custom Block 字段。
- 后代字段不会进入 Custom Block 的 PropertyEditor，也不能成为实例覆盖目录。

## 5. PropertyEditor 边界

PropertyEditor 始终只是通用的数据展示器和意图发射器：

```text
PropertyEditorInput
  = record + fields + display state

PropertyEditor
  -> emit({ sourceKey, fieldKey, value })
  -> emit add/reset/delete intent

Host / Command
  -> 决定写入蓝图 Block、instance.data、定义编辑状态或预览临时状态
```

Custom Block Host 在送入 PropertyEditor 前即时执行：

```text
读取 block.customBlockKey
-> resolver 取得 .ocblock
-> 读取 .ocblock.scheme
-> 与 Custom Block 固有结构字段及 additionalFieldDefinition 组成 fields
-> 将当前 record 原样作为展示 record
```

PropertyEditor 不负责查找 `.ocblock`、推导 root 默认值、合并蓝图与实例、决定写入位置、解析 Binding、生成 RenderReady、展开 root 或直接修改 record。

定义编辑、蓝图编辑、卡牌实例编辑和独立预览可以复用同一个 PropertyEditor，但必须由各自 Host 提供 projection 和 command。

### 5.1 Record、Ready 与默认值

```text
StoredRecord
  -> 宿主投影（文档场景可包含 instance）
  -> Binding resolve
  -> RenderReady parser
  -> RenderReady
  -> renderer

StoredRecord + resolved scheme + editor context
  -> PropertyEditorInput
```

- StoredRecord 是直接 JSON 事实，允许缺字段和未知字段；存储不得按 scheme 筛选或补写。
- RenderReady 是 parser 的只读输出，不是补全后的 StoredRecord，也不能反向写回。
- Binding 是从 `self`、`parent`、card、project 等 scope **取用值**，不是把参数塞进某个目标字段的机制。
- renderer 所需的缺失或非法值 fallback 由集中式 parser contract 提供，只保证 DOM 安全，不进入 PropertyEditor，也不写回 StoredRecord。
- `AdditionalFieldDefinition` 不保存 `defaultValue`。创建附加字段时，由 Host command 按 `fieldType` 调用统一初值策略，一次性写入初始 Stored 值。

### 5.2 Block 创建

Block 创建使用一个 `createBlock(type, init?)` 和一份完整 creator registry。registry 只为每种 Block 提供形成合法结构所需的种子，不读取 PropertyEditor scheme 的 `defaultValue`，也不为每种类型维护 `createXxxBlock()` 或大型独立模板体系。

Custom Block 的创建种子只负责 `id`、`type`、`customBlockKey` 等必要身份；当前 `.ocblock.scheme` 中缺失的字段保持缺失，不把 root 值复制进文档。

## 6. 普通 Block 的参考流水线

普通 Block 的职责顺序是目标基线：

```text
CardDocument + selected CardInstanceRecord
  -> applyInstance()
       文档宿主合并 instance.data[block.id]
  -> resolveReferences()
       统一解析 Binding
  -> prepareRichText()
  -> parseRenderDocument() / parseRenderBlock()
       原始字段 -> 稳定 RenderReady
  -> Block renderer dispatch
  -> 对应 renderer
  -> DOM
```

因此 renderer 的公开定义是：

```text
RenderReadyBlock + RenderContext -> DOM
```

renderer 不理解蓝图、实例或 PropertyEditor。CustomBlockRenderer 的调用方也只能提供 RenderReady 和 RenderContext；只有它在组合实现内部按结构引用读取 `.ocblock.root` 原始定义并重新进入共享准备管线。

## 7. Custom Block 外层流水线

### 7.1 文档中的 Custom Block

```text
CardDocument + CardInstanceRecord
  -> applyInstance()
       上层得到 Custom Block 载体的有效字段 record
  -> resolveReferences()
       按 Custom Block scheme 解析载体字段 Binding
  -> Custom Block RenderReady parser
       按 scheme 解析载体字段；缺失字段保持缺失，不从 root 反填
  -> RenderReadyCustomBlock
  -> CustomBlockRenderer
```

蓝图值和实例值的优先级只属于 `applyInstance()` 等文档宿主投影。CustomBlockRenderer 不接收 instance，不知道 CardDocument 的蓝图/实例概念，也不计算所谓“三层 Custom Block 值”。

### 7.2 独立使用和预览

独立预览没有实例概念：

```text
.ocblock + preview temporary record
  -> 按 .ocblock.scheme 执行 Binding / RenderReady parser
  -> RenderReadyCustomBlock
  -> CustomBlockRenderer
```

预览临时值不写入文档，也不得为了复用文档入口而构造 proxy `CardDocument`、伪造 CardFace 或伪造 instance。

## 8. `RenderReadyCustomBlock` 合同

Custom Block 必须是 RenderReady union 的正式成员：

```ts
type RenderReadyCustomBlock = RenderReadyBlockBase & {
  type: 'custom-block'
  customBlockKey: CustomBlockKey
  // scheme 字段位于顶层；只包含载体 parser 实际得到的字段
}
```

这里需要保留一个与 native Ready 不同但明确的缺失语义：

- `id`、`type`、`customBlockKey` 等 renderer 必需字段必须就绪。
- scheme 字段没有独立 `defaultValue`；源 record 缺失时，Ready 中也保持缺失或统一的空表示。
- parser 不能把 `.ocblock.root[field]` 反填到 Custom Block Ready。root 的值只在 CustomBlockRenderer 内作为结构默认值存在。

`RenderReadyCustomBlock[field]` 只表示该字段已经按 **Custom Block scheme** 完成外层 Binding 和值解析。它绝不是 root 类型的 RenderReady 字段。

## 9. CustomBlockRenderer

`CustomBlockRenderer` 是一个组合 renderer。它对外仍严格满足：

```text
RenderReadyCustomBlock + RenderContext -> DOM
```

内部流程固定为：

```text
1. 按 customBlockKey 取得 .ocblock definition
2. 克隆 definition.root 原始结构
3. 遍历 root 顶层字段
4. 若 RenderReadyCustomBlock 存在同名字段，则用该值覆盖 root 对应字段
5. 若不存在同名 Ready 字段，则保留 root 原始值
6. 将覆盖后的所有 root 字段统一视为 root 的原始输入
7. 以 root.type 对应的 scheme 重新执行：
     Binding resolve
     缺失/默认/fallback 处理
     RenderReady parse
8. 将 RenderReady root 交给正常 Block renderer dispatch
9. 得到 DOM
```

第 3 至第 5 步只是**同名字段覆盖**，不是 Binding，也不是参数注入。

最重要的类型边界是：

```text
Custom Block 的 RenderReady 值
  -> 覆盖 root 原始字段
  -> 成为 root parser 的原始输入
```

不能因为覆盖源已经是 `RenderReadyCustomBlock` 的字段，就把它误认为 root 的 RenderReady 字段。Custom Block scheme 和 `root.type` 的 scheme 是两套定义；覆盖值必须与未覆盖的 root 原始值一起，完整经过 root 的 Binding、默认处理和 RenderReady parser。

## 10. root 的身份与 Binding

root 是 Custom Block 载体的实现体，不是载体下面新增的一层逻辑 Block。

```text
外部存储：
container
  -> customBlockA

内部渲染：
container
  -> root（逻辑身份仍是 customBlockA）
       -> child
```

禁止解释成 `container -> customBlockA -> root -> child`。

由此得到固定 Binding 语义：

- root 的逻辑 `self` 就是外部 Custom Block 载体。
- root 中 `{{self:fieldName}}` 读取载体的 `fieldName`。
- root 中 `{{parent:sth}}` 读取载体在外部文档中的父 Block，例如 container。
- root 的直接 child 以 root/载体为 parent。
- 更深后代按正常 Block 树关系解释 `self` 与 `parent`。
- 富文本嵌入时，Custom Block 载体的 parent 是承载该嵌入的 Text Block。

例如 root 原始字段为：

```json
{ "xx": "{{self:fieldName}}" }
```

如果 `RenderReadyCustomBlock` 没有 `xx`，renderer 不覆盖它；随后 root Binding resolver 才把表达式解析为载体 `fieldName` 的值。这里没有“公开参数引用”或特殊 Binding 语法，只有正常的默认原始值和载体身份。

该身份模型应通过 Binding resolver 的上下文/owner 语义表达，不能通过 proxy CardDocument、虚拟 container 或永久 ID 改写伪造。

## 11. 递归、资源与错误边界

### 11.1 嵌套递归

root 最终得到的 RenderReady 如果仍是 Custom Block，就由正常 renderer dispatch 再次进入 `CustomBlockRenderer`。嵌套 Custom Block 是 renderer 组合的自然递归，不需要在正式 RenderReady 之前一次性摊平整棵结构。

RenderContext 必须携带当前结构调用栈。循环 identity 至少由“定义环境 identity + block key”组成，不能只按显示名或宿主 ID 判断。

### 11.2 资源环境

- `.ocblock.root` 中未被覆盖的固定值来自定义环境。
- 外部 Custom Block 载体字段来自调用环境，并在外层 Binding/Ready 阶段保留该来源。
- 将载体 Ready 值覆盖进 root 后继续解析时，不能按最终字符串猜来源；root 原始投影必须在运行时保留逐字段 provenance。
- 一个环境只能访问自己、宿主项目以及声明允许的直接子包；不能搜索兄弟包或用源项目环境兜底包预览。
- catalog、Blob URL、FontFace 和预览 URL 都绑定资源环境 identity 与 generation。

### 11.3 分级降级

- `.ocblock` 缺失：Custom Block renderer 输出稳定宿主 placeholder，并归属到该 Custom Block。
- definition JSON 无法形成可用 `scheme + root`：输出宿主 placeholder。
- 嵌套循环：只在循环调用位置输出 placeholder，外层其他内容继续渲染。
- 图片、字体、图标等局部资源错误：对应资源安全降级，其余内部内容继续渲染。
- 字段 Binding 类型错误：该字段使用所属 parser 的安全 fallback，其他字段继续处理。
- scheme 声明了 root 不存在的字段：字段覆盖被忽略，不因此判定整个 definition 非法。

诊断可以记录 Custom Block host identity 和递归调用路径，但 PropertyEditor 不得借诊断暴露或编辑后代内部字段。

## 12. 富文本嵌入

富文本中的 Custom Block 与文档中的 Custom Block 使用同一 definition resolver、scheme、载体 Ready parser 和 `CustomBlockRenderer`。它不是另一种 `packageId/properties` 协议。

已冻结行为：

- 持久化稳定的 embed identity、结构引用、载体字段和 `layout: 'inline' | 'block'`；不保存展开后的 root 或 RenderReady。
- `inline` 与 `block` 只改变排版，不改变字段解析或内部渲染结果。
- NodeView 是轻量 viewport；内部实现不可进入富文本编辑，整个嵌入节点可以选择、拖拽并打开属性面板。
- Binding 的 parent 是嵌入所在的 Text Block；root 的身份仍等于 Custom Block 载体。
- NodeView、RichTextPreview 和正式卡牌渲染必须调用同一组合 renderer，不得只显示 key 文本，也不得构造 proxy CardDocument。
- definition 缺失时显示稳定 placeholder。

富文本节点的最终序列化形状在实现前只需满足上述语义；不得为了适配旧 `values/properties` 再引入双格式。

## 13. 预览与导出环境

### 13.1 Custom Block 预览器

- 直接构造 Custom Block 的临时 StoredRecord/Ready 投影，不构造完整 CardDocument。
- PropertyEditor 只接收当前 customBlockKey 对应定义的 scheme 和临时 record，并 emit 意图给预览 Host。
- 使用目标资源快照调用同一 `CustomBlockRenderer`。
- Binding、root parser、资源缺失和循环诊断必须与正式环境一致。

### 13.2 导出器预览

- 先计算静态依赖、声明依赖、独立资源和嵌套包依赖闭包。
- 建立最终 package environment、catalog、access policy 和 generation。
- 在这个目标环境中解析 definition 并运行同一组合 renderer。
- 源项目环境不得作为 fallback，以免掩盖导出后缺失资源、越权作用域或包依赖错误。

## 15. 实施计划

### 阶段 A：协议和模型

1. 固定 `CustomBlock`、`CustomBlockDefinition.scheme`、`RenderReadyCustomBlock` 和结构引用类型。
2. 删除 `parameters`、`publicFieldKeys` 公开参数模型以及独立 `values/properties` 字段容器。
3. 让 definition resolver 返回当前 `.ocblock` 的 `scheme + root + definitionEnvironment`。

验收：Custom Block 与基础 Block 一样拥有顶层字段；更换 customBlockKey 后字段按 scheme/additional/Other 唯一分类。

### 阶段 B：编辑和外层准备

1. PropertyEditor Host 即时从当前 `.ocblock.scheme` 构造 fields。
2. 文档继续在 Custom Block renderer 之前完成蓝图/实例投影。
3. parser 按 Custom Block scheme 生成保留缺失语义的 `RenderReadyCustomBlock`。

验收：PropertyEditor 不知道 `.ocblock`，renderer 不知道 instance；缺失字段不会从 root 写回 Ready 或文档。

### 阶段 C：组合 renderer

1. 恢复/建立正式 `CustomBlockRenderer` dispatch。
2. 实现 Ready 同名字段到 root 原始字段的覆盖，并保留逐字段资源来源。
3. 以载体身份重新运行共享 Binding、default/fallback、RenderReady parser 和 renderer。
4. 通过 RenderContext 调用栈处理递归和循环。

验收：没有提前 native 展开；覆盖值和 root 默认值一起按 root scheme 重新解析；`self`、`parent` 语义符合第 10 节。

### 阶段 D：四种宿主

1. 文档画布直接渲染 `RenderReadyCustomBlock`。
2. 富文本 NodeView 与 RichTextPreview 接入同一组合 renderer，删除 proxy document。
3. 独立预览接入临时 record -> Ready -> renderer。
4. 导出预览接入最终 package environment。

验收：文档、富文本、独立预览和导出目标环境对同一调用得到一致内部 DOM；inline/block 只影响排版。

### 阶段 E：删除旧实现和测试重写

1. 删除 `expandCustomBlocks`、native placeholder 替换、host mapping 驱动正式渲染以及相关 shadow 约束。
2. 删除 proxy CardDocument、旧富文本 `packageId/properties/values`、重复预览路径和 legacy lookup。
3. 按本协议重写合同测试，不保留测试适配层。

核心测试合同：

- Custom Block 是 RenderReady union 的正式成员并由 renderer dispatch。
- root 只被同名 Ready 字段覆盖，缺失字段保留 `.ocblock.root` 原值。
- 覆盖后的值仍作为 root 原始值重新经过 root parser。
- root `self` 等于载体，root `parent` 等于外部父 Block，child `parent` 等于载体/root。
- 蓝图/实例投影只发生在文档 Host；独立预览不存在 instance。
- scheme、additional fields 和 Other 分类稳定且更换 customBlockKey 后无需迁移。
- 后代字段不进入 Custom Block scheme 或 PropertyEditor。
- 嵌套递归、循环 placeholder 和缺失 definition 都有稳定行为。
- 四种宿主共享 renderer；资源环境不会串用或被源项目 fallback 掩盖。

## 16. 明确删除的旧概念

生产代码、类型、测试、shadow 和当前文档最终都不得继续保留：

- Custom Block 在 RenderReady 前展开成 native subtree
- 正式 Ready 树中不存在 Custom Block
- Custom Block 没有自己的 renderer
- `parameters` / `publicFieldKeys` 是 Custom Block 字段身份
- `values` / `properties` 是文档 Custom Block 的独立字段容器
- root schema 被投影成外部参数定义
- Custom Block renderer 合并蓝图值和 instance override
- root 是载体下面新增的 Binding parent 层
- proxy CardDocument 或虚拟 container 用于预览和富文本 parent
- host mapping 代替 Custom Block 的正式 Block/renderer 身份
- 单块 ZIP `.ocblock`、`source`、`interfaceHash`、裸 key 或旧 identity fallback
