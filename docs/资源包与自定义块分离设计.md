# 资源包与自定义块分离：设计讨论记录

> 状态：方向已确认，部分 schema 与升级行为仍待定。本文记录当前共识与待决策项，不代表已经实现。

## 背景

当前自定义块的结构定义、发布身份、版本和资源环境被合并在同一个单块包中。运行时实际上已经通过切换资源根目录复用项目资源解析逻辑，但同一套资源服务多个自定义块时仍需导出、安装多份包，造成重复存储和重复管理。

新的边界应为：

- **自定义块是结构定义。**
- **资源包是资源上下文、运输边界和版本边界。**
- 块的运行时条目由“块定义 + 块所属资源环境”组合而成，而不是让块本身拥有一个包。

## 模块索引（并行边界）

> 以下模块按领域边界拆分，不代表执行顺序。所有模块共用同一个资源引用模型、资源环境模型和资源包数据合同。

### 模块 1：项目内部文件与基础数据模型

负责 `.opencard` 内部结构、旧内部协议文件移除、`.ocblock`/`.ocpack` 文件类型和基础身份合同。核心身份为 `block:key` 与 `package-key@block:key`。

### 模块 2：Custom Block 定义与注册目录

负责发现、读取和管理项目块与包内块，建立大小写不敏感 catalog，维护块所有权、只读包块、复制为本地块和 `public.blocks` 补全索引。

### 模块 3：资源包 manifest 与内容摘要

负责包级元信息、公开资源索引、直接子包依赖、宿主依赖和跨平台稳定的 SHA-256 `contentHash`。

### 模块 4：资源环境与包可见性

负责把宿主项目和每个包视为独立资源环境，管理 root、catalog、直接子包可见性、监听、generation 和运行时资源 session 生命周期。

### 模块 5：统一资源引用 parser/resolver

负责统一解析、规范化和格式化 `asset`、`font`、`icon`、`block` 引用，按当前环境、宿主项目和直接子包解析，并统一处理安全路径与诊断。

### 模块 6：运行时 Custom Block 展开与渲染

负责按块所属环境解析定义、应用实例字段覆盖、展开嵌套块、命名空间化内部 ID，并继续复用普通 Block 渲染管线。

### 模块 7：依赖分析与块资源声明

负责静态引用、动态 Binding、作者声明、独立资源和子包依赖的分析，生成导出依赖闭包；`.ocblock` 保存声明但不保存资源字节。

### 模块 8：资源包构建器与安装器

负责选择多个块和共享资源构建 `.ocpack`，生成 manifest、public、dependencies 和 contentHash，并安全校验、临时解压、确认后原子安装到 `.opencard/packages/<packageKey>/`。

### 模块 9：自动补全、选择器与预览

负责让块插入器、字体补全、图标选择器、富文本补全、Markdown 补全、块导出资源树和包构建器共用环境快照与 resolver。

### 模块 10：升级、卸载与资源生命周期

负责 package root 的版本替换、升级影响确认、取消回滚、卸载诊断、generation 切换以及旧资源 session 释放。

### 模块 11：统一诊断和测试合同

负责统一 `syntax-error`、`scope-unavailable`、`package-unavailable`、`dependency-mismatch`、`resource-unavailable`、`unsafe-path`、`type-mismatch`、`host-dependency` 和 `content-error` 等诊断分类及跨模块验证合同。


## 已达成的共识

### 自定义块

- 自定义块与资源包分离。
- 自定义块文件是项目级可注册、可管理的结构定义文件，主体接近当前包内的 `block.json`。
- 块文件描述根 Block、字段定义、字段可用性、尺寸编辑限制和声明式资源依赖，但不携带资源字节。
- 块不再拥有 publisher、包版本或其他发布信息。
- 导出块时直接编辑根 Block 的名称和块 Key；版本由包负责，不属于块。
- 块仍必须注册到项目的块目录/注册体系中，不能依靠扫描任意散落文件使用。
- 块导出工作台保留字段可用性、资源依赖树、预览和预览属性编辑器。资源树不再决定向 `.ocblock` 复制哪些资源，而是声明静态分析无法证明、尤其是动态 Binding 可能使用的候选资源。
- 块中的普通资源引用默认相对于块所属的资源环境解析。本地项目块默认使用项目资源环境；包内块使用所属包的资源环境。

### 资源包

- 资源包成为可同时容纳多个块和共享资源的运输与版本单元。
- 从项目的“文件 → 导出资源包”进入资源包构建工作台。
- 包信息至少包含名称、包 Key 和包版本。
- 包可包含字体、图标、自定义块、子包以及其他项目内图片。
- 资源包构建页不再显示为单个自定义块服务的字段可用性树。
- 选中块后，构建器自动计算其必需资源闭包。自动依赖在树中显示为 checked 且 checkbox 不可直接操作。
- 自动依赖不覆盖用户的显式选择状态：取消对应块后，应恢复该资源原有的显式 checked/unchecked 状态。
- 包解压后的安装目录本身就是资源环境根，并完整保留项目原有的相对目录结构；解析资源时只切换上下文根目录。
- 项目通过带资源类型的包限定引用访问已安装包中的资源，例如概念上的 `包Key@font:字体Key`；包版本不写入每一条资源引用。
- 纯块文件使用 `.ocblock`，是结构 JSON；资源包使用 `.ocpack`，是资源运输归档。
- `.ocpack` 必须解压展开到项目的 `.opencard/packages/<包Key>/`，不只保存 ZIP；该目录是包及其共享资源的所有权目录。
- 第一阶段的包依赖采用自包含内嵌子包，不要求宿主项目另行解析或下载外部依赖。
- `.opencard` 内原有 `.ocxx` 内部协议文件统一改为可识别的 `xx.json`；包清单固定为 `.opencard/manifest.json`。
- 只有位于 `.opencard` 内部的协议文件改用 `.json`。会被导入、导出、分享或由系统双击打开的文件继续保留 OpenCard 专属扩展名。

## 建议的数据边界

### 块定义

概念模型如下；字段名不是最终 schema：

```ts
type CustomBlockDefinition = {
  type: 'opencard-custom-block'
  key: string
  name: string
  root: CardBlock
  publicFieldKeys: readonly string[]
  declaredResourceDependencies: readonly string[]
}
```

尺寸限制可以继续规范化到根 Block 字段定义中，也可以保留独立的 `resize` 合同；应只保留一个真相来源。

块 Key 在其注册域内按大小写不敏感唯一：

- 本地块：项目块注册域；
- 包内块：该包的块注册域。

运行时不再以 `packageId` 代表块身份，而应使用独立的块引用，并把定义来源解析成对应资源环境：

```ts
type ResolvedCustomBlock = {
  definition: CustomBlockDefinition
  environment: ProjectResourceEnvironment
}
```

### 包清单

包 manifest 负责包级信息、公开资源接口、直接子包依赖和宿主资源依赖声明，不重复保存块的公开字段或资源 registry：

```ts
type ResourcePackageManifest = {
  type: 'opencard-resource-package'
  key: string
  name: string
  version: string
  public: PackagePublicResources
  dependencies: readonly PackageDependency[]
  hostDependencies?: readonly HostDependency[]
}

type PackagePublicResources = {
  blocks: readonly string[]
  fonts: readonly string[]
  iconSeries: readonly string[]
  assets: readonly string[]
}

type PackageDependency = {
  key: string
  version: string
  contentHash: string
}

type HostDependency = {
  kind: 'asset' | 'font' | 'icon' | 'block' | 'package'
  key: string
  requiredBy: readonly string[]
}
```

- `public.blocks`、`public.fonts`、`public.iconSeries` 和 `public.assets` 只决定自动补全、资源选择器和相关候选列表是否展示、排序或标记为包提供的资源。
- `public.iconSeries` 索引图标系列 Key，而不是单个 icon Key；公开某个系列后，自动补全可以展示该系列下的具体图标。
- `fonts.json`、`icons.json` 和其他 registry 保存完整运行时数据；manifest 的 public 列表只是 UI 索引，不是第二份 registry，也不是访问控制。
- 实际资源解析不检查 `public` 列表；只要 `package@kind:key` 的作用域合法、目标资源存在且路径安全，就允许解析。
- 包内公开块依赖的私有字体、图标和图片可以正常渲染；未列入 public 的资源仍可通过合法的显式引用取用。
- `dependencies` 是当前包的直接子包依赖锁定表，只记录直接依赖，不把传递依赖重复写入当前 manifest。
- `.opencard/packages/<key>/` 的物理目录已经表达依赖是内嵌的，因此不再增加冗余的 `embedded` 字段。
- 每条依赖记录包 Key、精确版本和内容摘要；版本用于显示和冲突诊断，`contentHash` 用于确认展开内容没有被替换、损坏或与声明不一致。
- 内容摘要采用跨平台稳定的 SHA-256 规范；输入是按规范化 `/` 路径排序的文件投影和文件字节，不依赖操作系统路径分隔符、目录遍历顺序或文件时间。
- 运行时解析 `subpackage@...` 时，只能使用 manifest 中声明且内容摘要匹配的直接子包；继续递归解析子包自己的 manifest。
- 内容摘要应覆盖子包的规范化内容投影，包括块文件、资源 registry、资源文件和子包 manifest；不包含父包引用该子包的 dependencies 条目本身，避免 manifest 自引用。
- `hostDependencies` 单独记录 `@...` 产生的宿主项目依赖，不能塞进 `dependencies`，因为它不属于包内可移植内容。
- 若资源被物化到当前包内，原本的宿主引用必须在导出转换中明确改写，不能同时保留错误的 `@` 语义。
- `dependencies` 不用于在线下载、SemVer 求解或全局包搜索；它是归档内容和运行时可见范围的完整性合同。
- 版本用于安装、升级、冲突提示和依赖锁定，不参与普通资源引用身份。

### 归档与安装形态

资源包扩展名确定为 `.ocpack`，纯块结构文件扩展名确定为 `.ocblock`。`.ocpack` 不设置特殊的 `resources/` 包装目录；归档根目录就是一个完整的最小项目投影：

```text
example.ocpack
├── .opencard/
│   ├── manifest.json
│   ├── project.json         # 仅在该投影确实需要项目策略时写入
│   ├── fonts/
│   │   └── fonts.json
│   ├── icons/
│   │   └── icons.json
│   ├── locale.json
│   ├── blocks/
│   │   ├── blocks.json
│   │   ├── badge.ocblock
│   │   └── frame.ocblock
│   └── packages/
│       └── dependency-key/...
├── assets/...
└── 用户选择的其他项目相对图片目录/...
```

这里不能引入名为 `resources/` 的特殊容器，因为它可能与用户自己创建的普通项目目录冲突。包内文件应保持其原项目相对路径，只有 `.opencard` 承担系统保留命名空间。

安装时必须把 `.ocpack` 安全、原子地解压展开到：

```text
<project>/.opencard/packages/<package-key>/
```

这个安装目录本身就是包资源环境的 `rootPath`，不是宿主项目环境的子目录，也不是再指向它下面的某个 `resources` 子目录。包内的图片、字体、图标和块都从这个包环境的项目结构中解析。包内块的注册目录是 `<packageRoot>/.opencard/blocks/`。

包 manifest 固定放在 `.opencard/manifest.json`。项目内部协议文件统一采用普通 JSON 名称，例如 `.opencard/project.json`、`.opencard/fonts/fonts.json`、`.opencard/icons/icons.json` 和 `.opencard/locale.json`；`.opencard` 目录本身已经提供了系统命名空间，不再需要 `.ocproject`、`.ocfonts`、`.ocicons`、`.oclocale` 这类二次隐藏命名。

### 内部协议文件与外部运输文件

内部文件名改为 `*.json` 不影响外部运输格式。以下文件仍保留产品专属扩展名：

- `.octemplate`：项目模板运输包；
- `.ociconpack`：图标包；
- `.ocblock`：纯自定义块结构文件；
- `.ocpack`：资源包；
- 其他需要跨项目传递、导入导出或双击打开的 OpenCard 文件。

实现该模型时必须同步修改 Tauri `fileAssociations`、外部打开白名单、文件选择器过滤器、图标与类型名称。特别是 `.ocblock` 的关联语义将从旧的“自定义块资源 ZIP”改为“纯块结构文件”，并新增 `.ocpack` 资源包关联。

## 包内块与项目块的注册规则

- 本地项目中，`<project>/.opencard/blocks/` 中存在块文件才表示本地块已注册。
- 资源包中，`<project>/.opencard/packages/<packageKey>/.opencard/blocks/` 中存在块文件才表示该包块已注册。
- 本地导出或导入的 `.ocblock` 直接注册到宿主项目的 `.opencard/blocks/`。
- 安装 `.ocpack` 时只将归档完整、原子地展开到 `<project>/.opencard/packages/<packageKey>/`；不把包块复制到宿主项目的 `.opencard/blocks/`。
- 本地块和包块都通过各自资源环境的注册目录被发现；包块的来源环境就是所属 package root。
- 包块保持 `packageKey@block:blockKey` 身份，本地块保持 `block:blockKey` 身份；同名块可以在不同环境中共存。
- 包 manifest 或等价的安装记录必须列出其包内注册块及内容身份，供升级、卸载和冲突检查使用。
- 卸载包时，删除整个 package root；引用这些包块或包资源的内容进入稳定的不可用状态。
- 包升级采用确认替换：先将新包解压到临时目录并完成校验，再展示版本、contentHash、块、字体、图标、资源和依赖的变化及影响范围；用户确认后才原子替换 package root。
- 用户取消或新包校验失败时，当前活动包和资源 session 保持不变；确认替换成功后，现有引用自动使用新版本，旧 generation 在新 session 接管后释放。

### 注册与解析示例

```text
项目/.opencard/blocks/local-badge.ocblock
项目/.opencard/packages/theme-pack/.opencard/blocks/badge.ocblock
```

它们分别对应：

```text
block:local-badge
theme-pack@block:badge
```

解析 `theme-pack@block:badge` 时，catalog 先定位 `theme-pack` 的 package root，再在该环境的 `.opencard/blocks/badge.ocblock` 中读取定义。不会去宿主项目的 `.opencard/blocks/` 猜测，也不会把包块复制到宿主块目录。

## 包引用建议

用户可见引用可以采用“包 Key + `@` + 包内引用”的形式，但应定义为结构化语法并由一个共享解析器处理，例如概念上的：

```text
my-package@block:badge
my-package@font:heading
my-package@icon:ui/check
my-package@asset:images/background.png
```

需要遵守：

- `@` 只表示进入包资源环境，不同时承担版本分隔符。
- 包内相对引用不必反复写包 Key；解析器已处于该包环境时，继续按普通项目语法解析。
- 项目显式取用包资源时才使用包限定形式。
- 引用解析后应得到 `{ packageKey, resourceKind, resourceKey }` 一类结构，不在各功能中分别用字符串切割。
- 包内解析默认不得悄悄回退到宿主项目资源，否则预览成功的包可能在其他项目失效。

已确定采用带资源类型的包限定语法；具体 `kind` 名称和图片路径细节仍待定。

## 包依赖建议

### 第一阶段：自包含的内嵌依赖（已确认）

建议第一版不引入运行时外部包依赖或 SemVer 求解器。导出的资源包应离线、自包含：

1. 选中块后计算直接及传递依赖。
2. 同包内的兄弟块直接复用该包资源，不形成子包。
3. 来自其他包的块或资源以子包形式内嵌，并记录精确的包 Key、版本和内容摘要。
4. 同一个 `包 Key + 版本 + 内容摘要` 在一个归档中只物化一次。
5. 包内引用优先且仅解析到其锁定的内嵌子包，不受宿主项目中同 Key 包的版本影响。
6. 构建时拒绝依赖环、同一包 Key 对应多个不兼容内容，以及超出深度、数量和体积限制的依赖图。

这与当前运行时的 scoped dependency catalog 很接近，但依赖对象从“一个块包”提升为真正的资源包。

### 暂不建议：导入后再寻找外部依赖

只在 manifest 写版本范围并要求宿主项目自行满足依赖，会立即引入：

- 缺包下载和离线失败；
- 一项目多版本共存；
- SemVer 范围求解与锁文件；
- 升级后的接口兼容性；
- 卸载保护和依赖来源选择；
- 同名包来源可信度与供应链问题。

在没有包仓库、签名和稳定兼容合同前，这些成本大于节省的少量跨包磁盘空间。先通过“一个包容纳多个共享资源的块”解决主要重复问题，再根据真实包体积决定是否增加外部依赖。

### 未来若需要外部依赖

建议采用“声明 + 锁定”而非只存版本范围：

- manifest 声明允许范围；
- 项目锁文件记录实际解析版本和内容摘要；
- 卡牌与块引用仍只写包 Key，不写具体版本；
- 同一项目第一阶段只激活每个包 Key 的一个版本；
- 包内构建预览必须使用锁定结果，并提供“一键内嵌依赖”作为可移植导出模式。

## 资源树状态模型

构建器不应只保存一个 `checked` 布尔值。建议至少区分：

```ts
type PackageSelectionState = {
  explicitSelected: ReadonlySet<ResourceId>
  requiredBy: ReadonlyMap<ResourceId, ReadonlySet<BlockId>>
}
```

最终选择为两者并集。展示规则：

- `requiredBy` 非空：checked + disabled，并显示“由哪些块需要”；
- 只有 `explicitSelected`：checked + enabled；
- 二者都为空：unchecked + enabled；
- 取消块只移除对应 `requiredBy` 来源，不修改 `explicitSelected`。

如果多个块依赖同一资源，必须等最后一个依赖来源消失后才解除强制选中。

## 需要特别避免的问题

- 不要把包版本写入卡牌中的每个资源或块引用，否则普通升级会造成全项目引用改写。
- 不要让包内资源隐式回退到宿主项目；这会破坏可移植性和真实预览。
- 包块位于自己的 `.opencard/blocks/` 并由包拥有；用户修改包块应复制为本地块，不得把包块复制到宿主 `.opencard/blocks/` 作为默认安装方式。
- 不要在 `.ocpack` 内增加特殊 `resources/` 包装层；归档根和安装目录本身就是项目式资源根，普通目录名必须留给用户。
- 不要让块 Key 同时承担包 Key；两者生命周期、唯一域和升级语义不同。
- 不要沿用 `.ocblock` 同时表示“纯块 JSON”和“资源 ZIP”。二者应使用不同扩展名或明确不同的文件签名。
- 不要一开始实现完整的在线依赖解析；先以自包含子包保持确定性。

## 待决策项

1. 块的尺寸限制继续放在根 Block 字段定义，还是保留独立 `resize` 字段。
2. 包升级和卸载如何识别 package root 是否被用户直接修改，以及用户是否允许直接编辑包内文件。
3. 同一包中选中的多个块若 Key 冲突，构建器应阻止导出还是允许导出时重命名；建议阻止并要求先在块定义中解决。
4. 包内块是否全部注册，还是允许“随包携带但不注册”；建议 manifest 明确列出注册块。

## 渲染、解析与自动补全讨论提案

> 状态：引用与混用的核心方向已确认，其余条目标明建议或待决策。

### 唯一资源引用语言

建立一个共享的资源引用模块，统一负责解析、规范化、格式化和诊断：

```ts
type ResourceKind = 'asset' | 'font' | 'icon' | 'block'

type ResourceReference = {
  scope: 'current' | 'host' | 'package'
  packageKey?: string
  kind: ResourceKind
  key: string
}
```

- 引用的包限定符有三种状态：无 `@`、空包 Key 的 `@`、非空包 Key 的 `packageKey@`。
- 无 `@` 的相对引用从当前文件/块所在资源环境解析；例如包内 Block 的 `asset:xx.png` 从该包根目录解析。
- 空包 Key 的 `@asset:xx.png` 强制从当前打开项目的资源环境解析；当前文件位于任意深度的包或子包时，仍回到宿主项目根。
- 非空包 Key 的 `subpackage@asset:xx.png` 从当前文件所在资源环境的 `.opencard/packages/subpackage/` 查找目标包，并以该包根作为资源上下文。
- 包限定引用的查找不是全局查找，也不直接拼接用户输入路径；先从当前环境的 package catalog 查找包 Key，再取得受信任的 package root。
- `/xx.png`、盘符路径、协议不允许的绝对路径和路径穿越形式一律判为非法，不把 `/` 猜测成项目根或包根。
- 所有 Key 和路径规范化只能由共享模块完成。渲染器、自动补全、依赖分析、富文本、Markdown 和导出器不得分别切字符串或维护正则。
- 共享模块返回结构化错误码，例如未知包、未知类型、缺少资源、不安全路径和类型不匹配；用户界面只显示本地化结果。

### 字段环境与显式包引用

继续保留字段级 `resourceScopes`，但其职责是提供当前字段所在的默认文件环境：

1. 无 `@` 的相对引用在字段默认环境中解析。
2. `@kind:key` 跳转到宿主项目环境。
3. `packageKey@kind:key` 从字段默认环境的包 catalog 找到目标包后切换环境。
4. 公开字段覆盖值仍继承调用方字段环境；覆盖值中的 `@` 或 `packageKey@` 具有与块内部引用相同的强制作用。
5. Binding 求值不会自动改变环境；结果字符串中的作用域前缀决定最终解析环境。
6. 包环境中的非限定引用不得回退宿主项目；只有显式空包 Key 的 `@` 才能回到宿主项目。
7. 包环境中的 `subpackage@...` 只访问该包环境下可见的子包，不访问宿主项目全局 packages 目录。

这样可以表达“包内固定资源”“宿主项目资源”和“当前包的相邻子包资源”三种需求，同时不需要改写包内 `.ocblock` 的原始字符串。

字段的来源环境仍需保留，因为无 `@` 的相对引用依赖它；但 `@` 和 `packageKey@` 会覆盖这个默认环境。一个字段可以混用多个包。

### 渲染管线

建议的新顺序：

1. 应用卡牌实例覆盖。
2. 按块引用解析已注册 `.ocblock`，得到块定义和定义来源环境。
3. 应用公开字段覆盖，并记录每个字段的默认环境来源。
4. 命名空间化内部 Block/location ID。
5. 递归展开自定义块并按解析后的块身份检测循环。
6. 展开 binding。
7. 每个图片、字体项、图标节点和富文本嵌入块通过统一引用解析器逐项解析。
8. 执行类型解析、布局和普通 Block 渲染。

需要改变当前的几个接口：

- 图标不能再使用“为整个字段返回一个 catalog”的 `resolveIconCatalog(blockId, fieldKey)`；应改为按单个图标引用解析，否则同一富文本无法混用项目与包图标。
- 字体回退列表必须逐项解析；同一个 `fontFamily` 字符串可以包含项目字体、多个包字体和系统字体。
- 富文本嵌入块必须逐节点解析块引用，不能先为整个富文本选择一个 Custom Block catalog。
- 图片和 Markdown 图片已经接近逐引用解析，但也必须改用共享引用 AST，而不是直接把原字符串拼到 rootPath。

### 块身份与循环检测

- 循环检测使用解析后的稳定身份，例如 `project:block:key` 或 `package:pkg-key:block:key`，不能只比较裸块 Key。
- 多实例 ID 命名空间继续以实例 ID 为根，避免同一块多次展开时 DOM、字段和 location 冲突。
- `.opencard/blocks/` 的注册路径、块引用身份和来源包所有权必须形成唯一映射；大小写不敏感冲突在注册阶段阻止。

### 包内原样存储与运行时来源

包内 `.ocblock` 文件按原样保存，不在安装或打包时把 `xx.png` 改写成宿主项目路径。运行时通过定义条目的来源环境解释它：

```ts
type ScopedResourceValue = {
  value: string
  environment: ProjectResourceEnvironment
}
```

以图片字段为例：

- 项目块写 `asset:xx.png`：从项目根解析。
- 包 A 内 Block 写 `asset:xx.png`：从包 A 根解析。
- 任意包内 Block 写 `@asset:xx.png`：从当前打开项目根解析。
- 包 A 内 Block 写 `subpackage@asset:xx.png`：从包 A 的 `.opencard/packages/subpackage/` 取得子包根，再解析 `xx.png`。
- 包 A 内 Block 写 `@asset:xx.png`，不能在导出包时把项目的 `xx.png` 静默复制进包后就丢失这个语义；应保留 `@` 引用，或在导出时明确执行“物化为包内资源”的转换。
- 公开字段由项目实例传入 `xx.png`：从调用方项目环境解析。
- 公开字段由项目实例传入 `subpackage@asset:xx.png`：从调用方项目环境下的 `subpackage` 包解析。
- 这条来源规则同样适用于字体、图标、Markdown 图片和富文本字段中的资源 token。

### 自动补全

自动补全必须消费与渲染器相同的环境快照和引用格式化器：

- 默认先显示字段当前环境中的资源。
- 输入 `@` 时切换到当前打开项目资源；输入非空包 Key 加 `@` 时，在当前文件环境下查找该包。
- 插入当前文件环境资源时使用无包前缀形式；插入宿主项目资源使用 `@kind:key`；插入当前环境下的其他包资源使用 `包Key@kind:key`。
- 候选项显示资源名称、Key、来源（项目或包名）和可用状态；相同显示名不能隐藏真实来源。
- 字体、图标、块候选从轻量 manifest/index 获取，预览字节和完整块结构按需加载，不能为了打开补全菜单加载所有包。
- 已卸载、损坏或未导出的包资源不作为正常候选；已存在于字段中的失效引用仍应显示“不可用”诊断而不是被清空。
- 富文本工具栏、属性输入框、Markdown 补全和块插入器共享候选服务，不各自构建 project-only catalog。
- 补全缓存键必须包含环境 identity 与 generation，不能只用原始查询文本。

### 依赖分析与导出

- 依赖分析直接遍历共享解析器产生的 `ResourceReference`，不得继续用正则猜测字体、图标、块和图片引用。
- 无 `@` 引用形成当前文件环境内的资源依赖；`@...` 引用形成宿主项目依赖；`packageKey@...` 引用形成当前文件环境下目标包的依赖。
- 这是三种不同的解析作用域，不应在 AST 中都表示为 `packageKey: null`。
- 导出器遇到 `@...` 时必须产生“宿主项目资源依赖”诊断或提供明确的物化选项；不能假装包已自包含。
- `packageKey@...` 在导出时应递归收集当前包环境下的目标子包，不能改为解析导出宿主项目的同名全局包。
- 同一资源被多个块引用时，`requiredBy` 保存所有来源。
- 同包兄弟块只形成同包内容依赖；跨包引用形成内嵌子包依赖。
- 构建预览必须只使用最终候选包环境，不允许宿主项目 fallback 掩盖遗漏。
- 动态 Binding 生成资源引用而无法静态确定依赖时，由块作者在块导出资源树中显式声明候选资源。`.ocblock` 只保存声明，不保存资源字节。
- 构建 `.ocpack` 选择块时，静态依赖与声明依赖共同进入 `requiredBy`；声明了但当前静态分析未引用的资源不得作为“无用资源”自动删除。
- 块导出资源树中的自动依赖保持 checked + disabled，作者勾选状态单独保存为 `declaredResourceDependencies`，不能把自动分析结果重复固化进块文件。

### 安全与生命周期边界

- 包 Key 只能先查安装 catalog 再得到 rootPath，禁止直接把包 Key 拼接进文件系统路径。
- `asset` 路径继续拒绝绝对路径、盘符、空段、`.`、`..`、反斜杠逃逸和符号链接。
- 普通 `asset` 引用不应允许读取 `.opencard` 内部协议文件；字体、图标、块和子包通过各自类型化 resolver 访问。
- 包内资源默认从包环境解析；显式 `@...` 可以声明宿主项目资源依赖。包内远程资源应在构建时物化；安装后的包环境默认禁止运行时远程回源。
- Package Environment、字体 FontFace、图标 catalog 和预览 URL 都带 generation，并由可释放 session 拥有。升级包时先在临时目录构建新 generation，成功后原子接管并释放旧 generation。
- 缓存身份必须包含环境 identity/generation、资源类型和规范 Key，避免不同包同名资源串用。
- 渲染器只消费解析服务返回的安全 URL、CSS 字体族、图标条目和块定义，不直接访问安装目录。

### 已确认的解析行为

1. 本地块引用使用显式 `block:key`。
2. 注册包块保持 `包Key@block:块Key` 身份，不因复制到项目注册目录而变成本地身份。
3. 同一个富文本字段或字体回退列表允许混用项目资源和多个包资源，因此 resolver 必须逐引用工作。
4. 动态 Binding 的资源依赖由块导出资源树显式声明，`.ocblock` 不携带资源字节。
5. 非空 `packageKey@...` 从当前文件环境的 `.opencard/packages/<packageKey>/` 查找目标包；空包 Key 的 `@...` 直接回到当前打开项目环境；不会全局搜索其他包。
6. 包内 Block 的固定相对资源引用使用块所属包环境；公开字段覆盖值保留调用方环境，不能按最终字符串重新猜测来源。

## 一体化重构计划

这不是分阶段兼容改造，而是一次性把“本地块、包块、资源环境和运输包”统一到同一套模型。旧的单块包模型、`publisher/block` 块身份、包内 `resources/` 特殊目录和旧 `.ocxx` 内部文件名在切换时直接移除，不保留双读、双写或兼容分支。

### 一、磁盘模型与所有权

```text
项目/
└── .opencard/
    ├── project.json
    ├── locale.json
    ├── fonts/
    │   └── fonts.json
    ├── icons/
    │   └── icons.json
    ├── blocks/
    │   ├── blocks.json
    │   └── local-badge.ocblock
    └── packages/
        ├── packages.json
        └── theme-pack/
            ├── .opencard/
            │   ├── manifest.json
            │   ├── fonts/
            │   │   └── fonts.json
            │   ├── icons/
            │   │   └── icons.json
            │   └── blocks/
            │       ├── blocks.json
            │       └── badge.ocblock
            └── assets/...
```

- `.opencard/blocks/blocks.json` 只登记本地块，`.opencard/blocks/*.ocblock` 是登记项引用的结构文件。
- `.opencard/packages/<key>/.opencard/blocks/blocks.json` 只登记该包拥有的块，旁边的 `.ocblock` 是登记项引用的结构文件。
- 安装包只展开到自己的 package root，不复制块到宿主 `.opencard/blocks`。
- 包内块默认只读；复制为本地块才改变所有权和资源环境。
- `.ocblock` 是纯结构文件，可外部传输但不含资源字节；`.ocpack` 是完整项目投影的运输归档。
- `.opencard` 内部协议文件统一使用 `*.json`，包 manifest 固定为 `.opencard/manifest.json`。

### CardDocument 中的实例边界

自定义块定义和自定义块实例属于不同层次：

```text
CardDocument.faces[*].children[*].block
└── type: 'custom-block'
    ├── id: 实例自己的稳定 ID
    ├── customBlockKey: block:key 或 packageKey@block:key
    └── 公开字段覆盖值，例如 width、height 和作者声明字段

CardDocument.instances[]
└── 卡牌数据表实例数据，不保存自定义块结构定义
```

`.ocblock` 只保存可复用的结构定义和声明式资源依赖；它不保存上述宿主实例 ID、实例覆盖值、包版本或资源字节。

### 二、统一资源引用与作用域

共享 parser 解析全部资源引用，AST 必须区分：

```ts
type ResourceReference = {
  scope: 'current' | 'host' | 'package'
  packageKey?: string
  kind: 'asset' | 'font' | 'icon' | 'block'
  key: string
}
```

规则固定为：

```text
asset:xx.png              当前文件所在环境
@asset:xx.png             当前打开项目环境
subpackage@asset:xx.png  当前文件环境下的 subpackage
```

同样适用于 `font`、`icon` 和 `block`。解析过程不能只传递最终字符串，必须传递默认环境和引用 AST；显式作用域覆盖默认环境。

### 三、环境 catalog 与依赖图

每个资源环境拥有：

- 自己的 rootPath；
- 自己的 `fonts/fonts.json`、`icons/icons.json`、`blocks/blocks.json` 与块定义 catalog；
- 自己的直接子包 catalog；
- 自己的 generation 和可释放资源 session；
- 对宿主项目环境的受控引用。

解析包 Key 时只允许：

- 空包 Key：宿主项目环境；
- 非空包 Key：当前环境直接子包；
- 不允许全局搜索、父包反查或兄弟包越级访问。

依赖图必须记录：

- 当前环境资源；
- 宿主项目资源；
- 当前环境下的子包资源；
- 动态 Binding 的声明依赖；
- 每条依赖的来源 Block、字段和引用位置。

### 四、块导出与资源声明

块导出界面保留：

- 根 Block 名称和 Key；
- 左侧字段可用性；
- 资源依赖树；
- 右侧预览；
- 预览属性编辑器。

资源树同时承担两种信息：

- 静态分析引用：自动 checked + disabled；
- 作者声明依赖：checked + enabled，写入 `.ocblock` 的声明列表。

`.ocblock` 只写结构、公开字段和声明依赖，不写资源二进制、不写 publisher、不写包版本。删除 Binding 后只提示声明可能过期，不自动删除作者声明。

### 五、资源包构建

用户选择多个块后，构建器合并：

```text
静态依赖
+ 块声明依赖
+ 选中的独立资源
+ 递归包依赖
= 包内容闭包
```

构建器必须区分：

- 当前项目资源：可复制并改写为包内相对引用；
- 当前包子包资源：以锁定包内容嵌入或引用；
- `@...` 宿主资源：保留宿主依赖，或由用户明确选择物化；
- 无法解析的静态依赖：阻止导出；
- 动态声明依赖：按声明加入，并在 manifest 中记录。

不会静默把 `@asset:xx.png` 改成 `asset:xx.png`。若用户选择物化，必须是明确的导出转换，并更新依赖记录。

### 六、运行时渲染

统一渲染顺序为：

1. 读取卡牌实例。
2. 解析 `block:key`、`@block:key` 或 `package@block:key`。
3. 得到块定义和定义环境。
4. 克隆块结构并应用公开字段覆盖。
5. 固定值使用定义环境，覆盖值使用调用方环境。
6. 为内部 Block/location ID 加实例命名空间。
7. 递归展开嵌套自定义块并检测完整环境身份循环。
8. 展开 Binding。
9. 对每个图片、字体、图标和富文本块引用逐条解析作用域。
10. 转换为普通 RenderReady Block。
11. 继续使用现有 NativeBlockRenderer 管线。
12. 在外层保留 CustomBlockRenderer 作为选择、定位和错误边界。

Custom Block 不拥有第二套渲染器；它仍然是“引用 → 展开 → 普通 Block 渲染 → 外层包回”的边界容器。

### 七、自动补全与预览

自动补全、块选择器、字体选择器、图标选择器、富文本和 Markdown 全部使用同一 parser、resolver 和 environment snapshot：

- 当前环境资源不加前缀；
- 宿主项目资源插入 `@kind:key`；
- 当前环境子包资源插入 `package@kind:key`；
- 候选显示来源环境、Key、名称和可用状态；
- 缓存包含环境 identity 与 generation；
- 预览加载哪一个环境，正式渲染就使用哪一个环境；
- 不允许宿主项目 fallback 掩盖包内缺失。

### 八、安装、升级与卸载

安装 `.ocpack`：

1. 校验归档路径、大小、条目、JSON、包 Key 和目录结构。
2. 解压到同文件系统临时目录。
3. 校验 manifest、包内 registry、块依赖和资源引用。
4. 生成 package environment 与 resource session。
5. 原子替换 `.opencard/packages/<key>`。
6. 重新发现该包及其子包。

升级采用确认替换：同一个 package Key 只保留一个活动版本；新包先在临时目录校验并展示版本、contentHash、块、字体、图标、资源和依赖变化及影响范围，用户确认后才原子替换。版本不写入卡牌引用；确认替换成功后现有引用自动使用新版本，旧 generation 在新 generation 接管后释放。卸载删除 package root，相关实例和资源引用显示稳定的不可用诊断。

### 九、必须建立的测试合同

- 本地块和包块同名时分别解析到正确环境；
- 三层嵌套包的无前缀、空包前缀和非空包前缀；
- 公开字段覆盖不错误继承块环境；
- 同一富文本混用项目、当前包和子包图标；
- 字体 fallback 跨环境且顺序正确；
- `@` 宿主资源依赖被导出器正确识别；
- 同名包不会被全局错误解析；
- 包升级 generation 不串资源；
- 缺失资源只影响对应资源或块；
- 自动补全插入的文本可被正式 resolver 解析；
- 导出后的 `.ocpack` 在另一项目中按相同作用域规则运行；
- 路径穿越、绝对路径、符号链接和未授权 `.opencard` 访问全部被拒绝。
