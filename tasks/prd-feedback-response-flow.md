# PRD：反馈回执与官方答复链路

## 1. Introduction / Overview

OpenCard 已能通过 Cloudflare Worker 将用户反馈提交到私有 GitHub 仓库，但用户提交后只能获得一次性的报告编号，无法在应用内确认处理进度或查看答复。

本功能新增“我的反馈/建议”入口。每次提交成功后，应用在当前设备保存报告编号和一枚私密回执令牌；用户可在应用内查看反馈状态及一条官方答复。维护者继续在私有 GitHub Issue 中处理反馈，Worker 直接根据 Issue 是否关闭及是否存在可信评论推导用户状态，无需维护标签或评论标记。

该链路不要求 OpenCard 账号，不公开原始反馈，不把用户引导到 GitHub，也不提供多轮对话。

## 2. Goals

- 让用户提交后能确认反馈已被接收，并在同一设备上再次找到它。
- 让用户在 OpenCard 内查看明确的处理状态和一条可更新的官方答复。
- 让维护者继续使用 GitHub Issue 作为唯一处理后台，不新增管理站点。
- 使用不可猜测的本地回执令牌保护私有反馈查询，不要求用户注册或登录。
- 保证查询接口只返回面向提交者的最小信息，不泄露私有仓库、内部评论、标签或诊断详情。

## 3. User Stories

### US-001：提交后生成并保存回执

**Description:** 作为提交反馈的用户，我希望提交成功后自动保存回执，以便稍后查看处理结果。

**Acceptance Criteria:**

- [ ] `POST /feedback` 成功响应包含 `reportId`、一次生成的回执令牌、初始状态和提交时间。
- [ ] 回执令牌具有足够随机性，无法根据 `reportId`、Issue 编号或其他公开信息推导。
- [ ] 服务端仅持久化令牌的不可逆摘要，不持久化或记录明文令牌。
- [ ] 客户端只在提交成功后写入本地回执；提交失败时不产生虚假记录。
- [ ] 重复响应或界面重渲染不会产生重复的本地记录。
- [ ] 现有反馈提交能力保持兼容，类型检查与相关测试通过。

### US-002：显示“我的反馈/建议”列表

**Description:** 作为用户，我希望从“反馈与帮助”区域查看本设备提交过的反馈，以便找到报告编号和当前状态。

**Acceptance Criteria:**

- [ ] “反馈与帮助”区域提供可发现的“我的反馈/建议”入口。
- [ ] 列表显示反馈类型、标题、报告编号、提交时间和最近一次已知状态。
- [ ] 没有本地回执时显示明确空状态，不发起查询请求。
- [ ] 单条记录查询失败时保留上次成功状态，并显示可重试提示，不影响其他记录。
- [ ] UI 文案提供现有项目支持的本地化版本。
- [ ] 类型检查、UI lint 与相关组件测试通过。
- [ ] Verify in browser using dev-browser skill.

### US-003：批量查询未关闭反馈状态

**Description:** 作为持有回执的用户，我希望用一次刷新查看所有未关闭反馈是否已收到、已答复或已关闭，以便减少请求并了解处理结果。

**Acceptance Criteria:**

- [ ] 客户端把全部本地非 closed 回执合并到一次批量请求中，不把令牌放入 URL 查询参数。
- [ ] Worker 验证令牌摘要与报告的绑定关系后才访问对应 GitHub Issue。
- [ ] 查询结果仅包含 `reportId`、用户可见状态、提交时间、更新时间和可选官方答复。
- [ ] 无效、缺失或不匹配的令牌返回统一的未授权响应，不透露报告是否存在。
- [ ] GitHub Issue 不存在或不可访问时返回稳定的服务错误，不暴露仓库信息。
- [ ] 打开历史记录时只刷新 `nextCheckAt` 已到期的非 closed 回执，并合并为一次批量请求；切换记录不请求网络。
- [ ] 普通模式不提供手动刷新按钮，不在应用启动或后台定时轮询；没有到期记录时产生零次请求。
- [ ] 仅开发者模式显示“强制刷新”，它忽略 `nextCheckAt`，但仍把全部非 closed 回执合并为一次批量请求并受同一限流约束。
- [ ] 本地已为 closed 的回执永远不再发送；网络失败按 15 分钟、30 分钟、最多 1 小时退避。
- [ ] Worker 单元测试、类型检查和 dry-run 通过。

### US-004：从 GitHub 原生状态推导用户状态

**Description:** 作为维护者，我希望评论或关闭 GitHub Issue 就能更新用户状态，以便不再重复维护标签。

**Acceptance Criteria:**

- [ ] Open 且没有可信评论的 Issue 显示为“已收到”。
- [ ] Open 且存在可信评论的 Issue 显示为“已答复”。
- [ ] Closed Issue 显示为“已关闭”，并覆盖是否存在评论。
- [ ] 状态推导不读取或要求任何 `status:*` 标签。

### US-005：发布并更新一条官方答复

**Description:** 作为维护者，我希望在 GitHub Issue 内编写一条可编辑的官方答复，以便用户在 OpenCard 中看到结论。

**Acceptance Criteria:**

- [ ] 评论必须由具备目标仓库写入权限的账号或当前已授权 GitHub App 创建。
- [ ] 用户侧最多显示一条官方答复；存在多条可信评论时采用最后更新的一条。
- [ ] 维护者编辑同一条评论后，用户下次刷新能看到更新后的内容与更新时间。
- [ ] Worker 将答复限制为纯文本与换行；不向客户端下发可执行 HTML。
- [ ] 没有官方答复时详情页显示与当前状态一致的说明，不显示内部评论。

### US-006：查看反馈详情与官方答复

**Description:** 作为用户，我希望在反馈详情中看到提交摘要、状态和官方答复，以便理解处理结果。

**Acceptance Criteria:**

- [ ] 详情页显示本地保存的类型、标题、提交时间和报告编号。
- [ ] 官方答复区域清楚区分“尚无答复”和实际答复，并显示答复更新时间。
- [ ] 官方答复按纯文本安全渲染，换行可读，链接不自动获得危险协议能力。
- [ ] 状态变化不覆盖或篡改本地保存的原始提交摘要。
- [ ] 网络不可用时仍能查看本地摘要和最后一次成功同步的状态/答复。
- [ ] 类型检查、UI lint 与相关组件测试通过。
- [ ] Verify in browser using dev-browser skill.

### US-007：删除本地反馈记录

**Description:** 作为用户，我希望移除本设备上的反馈回执，以便管理本地记录。

**Acceptance Criteria:**

- [ ] 删除前明确提示：此操作只删除本地回执，不会撤回或删除已提交的反馈。
- [ ] 确认后删除该记录及其明文回执令牌、缓存状态和缓存答复。
- [ ] 删除操作不调用 GitHub，不修改 Worker 数据，也不改变反馈处理状态。
- [ ] 删除后，若用户未另行保存令牌，应用不提供恢复能力。
- [ ] 取消确认不会改变任何数据。
- [ ] 类型检查与相关组件测试通过。
- [ ] Verify in browser using dev-browser skill.

### US-008：保护查询接口与隐私边界

**Description:** 作为用户，我希望只有持有本地回执的客户端能读取我的反馈结果，以免私有内容被枚举或泄露。

**Acceptance Criteria:**

- [ ] 查询接口沿用反馈服务的来源限制、请求大小限制和速率限制策略，并为查询设置独立限额。
- [ ] Worker 日志不包含明文回执、反馈正文、诊断内容或官方答复全文。
- [ ] 响应不包含 GitHub 仓库名、Issue 编号、Issue URL、作者身份、内部标签或内部评论。
- [ ] `reportId` 不作为授权凭据；仅凭 `reportId` 无法查询反馈。
- [ ] 自动化测试覆盖令牌枚举、令牌与报告错配、无权限评论伪装答复和 GitHub 错误脱敏。
- [ ] 安全相关依赖和 Cloudflare 配置通过生产检查。

## 4. Functional Requirements

- **FR-1:** 提交反馈成功后，服务必须返回 `reportId`、`receiptToken`、`status` 和 `submittedAt`。
- **FR-2:** 服务必须为每条反馈生成独立的高熵 `receiptToken`；客户端必须将其视为秘密信息。
- **FR-3:** 服务必须在 Cloudflare D1 中保存 `reportId`、回执令牌摘要、GitHub Issue 内部定位信息和创建时间；不得保存明文令牌。
- **FR-4:** 客户端必须在本地持久化反馈类型、标题、报告编号、提交时间、明文回执令牌及最后一次成功查询的用户可见结果。
- **FR-5:** 查询必须使用认证请求头传递回执令牌，不得将令牌写入 URL、遥测或错误消息。
- **FR-6:** 查询接口必须对不存在的报告、错误令牌和令牌错配返回相同的外部响应。
- **FR-7:** Worker 必须使用 GitHub App 权限读取私有 Issue 的 open/closed 状态和评论，并转换为稳定的用户侧响应模型。
- **FR-8:** 用户可见状态仅为“已收到”“已答复”“已关闭”三种。
- **FR-9:** Closed Issue 必须显示“已关闭”；Open Issue 根据是否存在可信评论显示“已收到”或“已答复”。
- **FR-10:** Worker 只可返回最后更新的一条、作者具备仓库写入权限或来自当前 GitHub App 的评论作为官方答复。
- **FR-11:** 官方答复必须以纯文本返回并设定长度上限；超限时服务必须返回明确配置错误，不能静默截断造成语义变化。
- **FR-12:** “我的反馈/建议”必须只展示当前设备保存的回执，不得通过设备指纹、IP 或 GitHub 数据推测用户历史。
- **FR-13:** 打开反馈详情时必须尝试刷新该条记录；用户也可以手动刷新。
- **FR-14:** 查询失败时必须保留并标记最后一次成功结果，而不是将状态重置为初始值。
- **FR-14A:** 每次到期刷新必须把全部到期且非 closed 的回执合并为一次、最多二十条的批量请求；closed 与未到期回执不得发送。
- **FR-14B:** 首次检查约在提交后 30 分钟；已收到状态约每 6 小时检查，已答复状态约 24 小时后检查是否关闭；网络失败退避不得超过 1 小时，并加入时间抖动。
- **FR-15:** 删除记录只清除当前设备上的本地数据，不调用远端撤回或删除接口。
- **FR-16:** 所有新增用户界面必须使用现有 OpenCard 主题、对话框、列表、按钮和本地化体系。
- **FR-17:** 实现该用户可见功能时必须同步更新 `opencard-app/RELEASE_NOTES.md`。

## 5. Non-Goals / Out of Scope

- 不提供用户账号、登录、跨设备同步或云端反馈历史。
- 不提供多轮客服对话、用户追问、附件补交或实时聊天。
- 不让用户直接访问或参与私有 GitHub Issue。
- 不公开原始反馈，也不提供“转为公开 Issue”的流程。
- 不允许用户在应用内撤回、编辑或删除服务端反馈。
- 不新建维护者管理后台；维护者只使用 GitHub Issue。
- 不发送邮件、系统通知或推送通知；用户主动打开页面查看更新。
- 不导入该功能上线前已提交、但没有回执令牌的历史反馈。

## 6. Design Considerations

### 信息架构

- “发送反馈”和“我的反馈”共用一个名为“反馈与建议”的弹窗；顶部居中分页控件负责切换，两种菜单入口只决定初始页。
- 列表优先显示状态与标题，报告编号作为次要识别信息。
- 详情页分为本地提交摘要、处理状态、官方答复三个区块。
- 状态使用文字与现有语义色共同表达，不能只依赖颜色。
- “删除本地记录”放在详情页的次要危险操作区域，确认文案明确远端反馈不会被删除。

### 状态语义

| GitHub 条件 | 用户状态 | 用户含义 |
| --- | --- | --- |
| Issue 已关闭 | 已关闭 | 处理流程已结束，可能有或没有正式答复 |
| Issue 为 Open 且存在可信评论 | 已答复 | 最新一条可信评论作为用户可见答复 |
| Issue 为 Open 且没有可信评论 | 已收到 | 服务已接收，尚无答复 |

## 7. Technical Considerations

### 推荐数据流

1. 客户端向现有 `POST /feedback` 提交内容。
2. Worker 创建私有 GitHub Issue，并生成 `reportId` 与高熵 `receiptToken`。
3. Worker 将 `receiptToken` 的带密钥摘要和 Issue 定位信息写入 D1，然后把明文令牌仅返回给客户端。
4. 客户端把回执与提交摘要保存到本地反馈仓储。
5. 用户打开历史时，客户端筛选到期且非 closed 的回执，把其 `reportId` 与令牌放进一次 `POST /feedback/status` 批量请求；没有到期回执时只显示缓存。
6. Worker 验证全部回执后读取对应 GitHub Issue，根据 open/closed 与可信评论推导状态和答复。
7. 客户端缓存成功结果供离线查看；删除时只清除该本地缓存与令牌。

### GitHub 处理约定

- 创建 Issue 后无需附加状态标签。
- 维护者直接评论即可答复；最新评论成为当前用户可见答复，关闭 Issue 即进入终态。
- Worker 必须校验评论作者的仓库关联或 GitHub App 身份，不能信任外部评论。
- 该私有仓库中的可信评论视为面向用户的答复，不再承载不会公开的内部讨论。

### 存储与安全

- D1 表建议只承担回执授权映射：`report_id`、`token_digest`、`issue_number`、`created_at`、可选 `last_accessed_at`。原始反馈正文仍只存在于私有 GitHub Issue。
- 摘要应使用 Worker secret 参与的 HMAC 或等价方案，避免数据库泄露后可离线验证低质量令牌；令牌本身必须由密码学安全随机源生成。
- 客户端本地记录需要版本字段和容错迁移，单条损坏不能阻止其他回执加载。
- 本地存储不是身份系统：能读取用户设备数据的人可能获得回执访问能力，界面和文档需要明确这一边界。
- GitHub API 暂时不可用时使用短时错误响应，不将错误详情直接透传给客户端。
- 查询请求采用客户端持久化调度：记录 `nextCheckAt` 与 `failureCount`，只在历史页打开且有到期记录时请求，不运行后台计时器。

### API 响应边界示例

```ts
type FeedbackReceiptResponse = {
  reportId: string
  receiptToken: string
  status: 'received'
  submittedAt: string
}

type FeedbackStatusResponse = {
  reportId: string
      status: 'received' | 'answered' | 'closed'
  submittedAt: string
  updatedAt: string
  officialResponse?: {
    text: string
    updatedAt: string
  }
}
```

接口不得向客户端加入 `issueNumber`、仓库信息、GitHub URL、评论作者或原始标签数组。

### 交付顺序

1. 先扩展 Worker 的回执生成、D1 映射和受保护查询，并完成安全测试。
2. 再建立客户端本地回执仓储及服务层，不引入 UI。
3. 然后实现列表和详情的只读状态查看。
4. 最后补充本地删除、错误状态、浏览器验证和发布说明。

每个阶段保持独立测试和小范围 diff，避免把反馈 UI、GitHub 协议、持久化和网络错误处理重新堆回单一模块。

## 8. Success Metrics

- 100% 的成功提交响应都包含可用回执，并能在当前设备的“我的反馈/建议”中立即出现。
- 持有正确回执的查询能准确反映 GitHub open/closed 状态与最新评论；无回执查询成功率为 0%。
- 查询响应中不出现仓库名、Issue 编号、内部评论、诊断正文或明文令牌。
- 用户从打开“反馈与帮助”到看到某条反馈状态不超过 3 次交互。
- GitHub 正常可用时，一次批量状态查询的服务端 P95 响应时间目标低于 3 秒。
- 新功能上线后，反馈提交、现有 Shell 菜单和离线启动无回归。

## 9. Open Questions

- 本地回执最终使用现有应用偏好存储、独立持久化文件还是平台安全存储，需要在实现前结合当前 Tauri 存储能力确认；API 与 UI 不应依赖具体实现。
- 官方答复纯文本的最大长度需在实现时根据现有请求/响应上限确定，建议初始上限为 8 KiB。
- 是否为超过一定年限的 D1 回执映射设置保留期限尚未决定；在有明确隐私或成本策略前不自动过期。
